# Echo architecture and API v1

`internal/domain` defines Bot, Chat, Message, Run, ToolCall, ExecutionScope, PluginManifest and Event. The browser equivalents are in `web/src/types.ts`. Stable bot IDs are separate from unique case-insensitive handles. Messages persist structured text, mention and file-reference segments, recipients and historical author labels. Every event has a monotonic sequence and optional chat/run/bot IDs.

The Echo name is independent of storage identifiers. The default `%LOCALAPPDATA%\Echo2` profile, `echo2.sqlite` database, `Echo2/` credential targets, session cookie, saved window-layout keys and sandbox identities remain compatible with existing installations. Rebranding does not copy, reset or migrate user data. The `ECHO2_*` test environment switches also remain supported.

## Boundaries

- `store`: SQLite (modernc), WAL, compressed individual messages/chunks, transactional acceptance, retry deduplication, crash recovery and incremental reclamation. A data-directory lock prevents two servers performing recovery against each other. Streaming chunks flush every two seconds or 64 KiB and at completion/shutdown. Neither model streaming nor shell streaming rewrites the transcript on each token.
- `model`: compatible HTTP/SSE transport, fragmented tool calls, reasoning, connection deadlines, credential redaction and local-destination enforcement. Context summaries are model input only; `chat_search` can retrieve the original transcript.
- `contextmanager`: shared per-run accounting and overflow recovery for regular and inline chats. Provider input usage anchors an unchanged request prefix; only newly retained messages are estimated, including tool schemas and media allowances. Configuration changes and compression invalidate the baseline. Default limits are 32,768 tokens, a 70% proactive threshold, and 2,048 reserved output tokens unless configured otherwise. Usage is optional additive message metadata, not a sum across rounds.
- `coordinator`: fixed dispatch participants, deduplicated correlations, explicit send/reply/wait, circular-wait detection, failed-recipient notification and cancellation, with no request-count ceiling. Public responses never implicitly wake another bot.
- `broker`: root-relative file operations, bounded checked HTTP, Windows AppContainer/Job Objects, Linux bubblewrap, and macOS Seatbelt. Scope changes block new dispatches while existing runs terminate. Windows ACL cleanup targets only the unique Echo SID. Required runtime/toolchain access is read-only; workspaces and private temporary/cache directories are writable. Containment failure never falls back to unrestricted execution.
- `plugins`: wazero runtime with 64 MiB memory, a five-minute invocation deadline, cancellation, bounded output, immutable package digests, capability validation and previous-package rollback. Each invocation is a fresh WASI module. Built-in tools enter the same guest/host protocol. Native privilege remains in explicitly checked host operations.
- `calendar`: durable schedules and stable occurrence identities, server-side ticking, local-time recurrence and persisted missed-work reviews. Selection/skipping of a missed batch is transactional.
- `server`: owner authentication, API, WebSocket subscriptions, per-bot model loops and host-operation dispatch. Each bot has its own model history. Model loops have no round-count ceiling and end on a final response, error or cancellation. A scheduled prompt cannot add recipients by embedding a mention.
- `web`: independent Vite/TypeScript UI using Echo's design tokens and card/composer concepts, with a lazy built-in Monaco editor app. No runtime imports from legacy modules. The built-in Terminal owns a persistent bottom dock. Monaco includes provider-based Source Control; desktop automation remains separate.
- `swarm`: stable node identities, password pairing, persistent duplex links, topology, sealed relays and destination authentication. Coordination remains at the chat home; host-local execution owns all tools, models, workspaces and credentials.

## Context management

`contextmanager.Manager` separates retry policy from the injectable `Compressor` interface. The default `Summarizer` bounds individual summary inputs and outputs, recursively splits chunks rejected for context size, merges summaries with a progress limit, and preserves complete tool exchanges. A strategy receives the history, protected-message mask, target token budget and scoped completion callback. It must return smaller context, retain protected messages and tool pairing, and leave its input untouched. `Server.ContextCompressor` can replace the strategy without changing chat loops or recovery rules.

Proactive compaction follows the endpoint checkbox. Recognized context overflow always permits one compressed request, one minimal-context request, then at most one request per omitted tool result, skipping identical payloads. Minimal context protects system instructions, the current user request and latest relevant tool exchange; inline chat also protects its authoritative editor candidate. Tool payloads are omitted largest-first only after the minimal request is rejected. Combined overflow is described as such rather than attributed to an unmeasured individual result. Retries never execute tools or apply proposals. Unrelated errors and cancellation stop recovery. Required context that still cannot fit produces an actionable error.

Regular chat retries replace partial assistant snapshots and chunks; inline streams send a `reset` event containing the accepted answer prefix. Tool `modelContent` metadata stores model-facing omissions independently of original output and attachments, and prevents omitted generated images from being reloaded. Summaries and usage baselines are run-local; persisted usage does not calibrate a reconstructed history. No schema migration is needed.

The compatible transport requests streaming usage, reads usage-only events after finish reasons, and caches explicit rejection of `stream_options.include_usage` per connection/model. HTTP and SSE context errors retain typed overflow information through credential redaction. Generic payload limits, HTTP 413 without context evidence, and rate limits do not trigger context recovery. Custom providers may optionally return `usage:{inputTokens,outputTokens,totalTokens}` and `overflow:{message,limitTokens?,inputTokens?,outputTokens?}` alongside their existing result fields; `model.complete` preserves overflow through its host invocation even across the WASI error boundary.

## Usage accounting

Model completions record provider-reported usage on their execution host, including inline requests and context summaries. Input/output missing flags distinguish unknown values from reported zero; only known input establishes the context manager's baseline. Custom provider `model.complete` delegations are counted at the host call, suppressing the enclosing provider result's duplicate usage. Each request's final streaming snapshot is counted once, including reported usage retained before a later stream error.

The existing records store holds lifetime counters, reset baselines, request IDs, and reset receipts. Recording usage and the run's optional `statistics` metadata is transactional; replica merges, forks, and transcript reads do not count consumption. Run statistics retain the first execution start across handoffs and record elapsed wall time, tool calls started, model calls, token sums, and reporting coverage. A reset advances only the machine baseline, preserving run history and accepting in-flight requests into the new totals when they complete. No schema migration or historical backfill is required.

Authenticated `GET /api/v1/usage` returns counters since reset, coverage, tracking/reset times, and a revision. `POST /api/v1/usage/reset` accepts an idempotency `requestId`. General aggregates reachable instances by stable node identity, excludes offline/unsupported instances, and refreshes every five seconds while mounted and on directory updates. Development confirms a fixed reachable target list and retries unsuccessful resets with the original request ID. Footer visibility is browser-local.

## Swarm protocol and ownership

Swarm protocol version 1 negotiates `owner-api/1`, `dispatch/1`, `stream/1` and optional native app capabilities such as `native-monaco/1` and `native-terminal/1`. Unsupported peers receive an update-both-instances error. The built-in app-scoped plugin starts disabled. Only an explicit, password-authenticated pairing may activate an installed remote plugin; discovery cannot undo an owner disable, disconnect or revocation.

Swarm links can reconnect while the server is recovering its profile. An atomic readiness gate publishes initialized services only after server construction completes. Earlier tunneled requests receive HTTP 503 with `Retry-After: 1` before route construction; the established link can retry after startup. Shutdown revokes readiness before services are closed.

The persistent `nodeId` is the first 128 bits of the SHA-256 hash of an X25519 public key. Its private key is an owner-only profile file; the node record lives in the existing records table. This identity is independent of the process-specific health `instanceId`/event epoch. Resources use `{nodeId,id}` internally and `nodeId:id` in combined browser state. Local IDs and legacy local browser keys remain unchanged. Machine names are mutable labels, initially normalized hostnames; duplicates receive a stable ID suffix. Mentions resolve to identities before forwarding. Bare handles resolve at the browser's entry instance. Workers receive a fully qualified roster fixed by the current message.

| Route under `/api/v1` | Contract |
|---|---|
| `GET /swarm/peers` | Local identity and sanitized peer directory; no grant hashes or secret references |
| `POST /swarm/peers` | Explicit `{url,password,name?}` connection, or `{nodeId,password}` through a discovered route |
| `PATCH /swarm/peers/{nodeId}` | `{disconnected}` suspends/resumes a retained connection |
| `DELETE /swarm/peers/{nodeId}` | Revoke all grants and attempt reciprocal revocation |
| `POST /swarm/pair` | Versioned password handshake; no loopback/cookie password exemption |
| `GET /swarm/link` | Authenticated duplex WebSocket; deterministic duplicate-link selection |
| `GET /swarm/state` | Authorized target-local directory snapshots and availability |
| `GET /swarm/events` | Source-attributed directory/event notifications |
| `/swarm/instances/{nodeId}/…` | Owner API, streaming, uploads, downloads and subscriptions routed to the resource's host |

Each peer grant has independently generated inbound/outbound bearer tokens in host secret storage. A small rolling grant set permits crossed reciprocal handshakes without invalidating their accepted tokens. Password changes and revocation invalidate every affected grant; ordinary restart preserves them. Discovery credentials also live in secret storage. They authenticate the destination directly, including through a relay; B's C credentials never substitute for A authenticating C. Relayed payloads use X25519-derived AES-GCM sealing between their originating and destination identities. Paths and source/destination are authenticated associated data. Fresh receiver challenges bind data to an accepted stream and prevent replaying captured owner requests. Pairing-only streams can reach only the password handshake. Worker dispatch tokens cannot authorize owner APIs.

Topology consists of authenticated peer advertisements, without LAN scanning. Routes contain stable identities, reject repeated nodes, prefer the shortest direct path, and break ties deterministically. Discovery is concurrency-limited and backs off after failed authentication. There is no configured machine-count ceiling. Traffic uses 32 KiB frames, eight in-flight chunks per virtual connection, 256 queued link frames and 256 incoming streams per source; frame and directory messages also have explicit size bounds. Slow links fail and reconcile instead of retaining unbounded data. The existing HTTP, WebSocket, streaming buffer and snapshot machinery runs over flow-controlled virtual connections. Initial pairing inherits the confidentiality of the chosen HTTP(S) origin; encrypted relay traffic does not make an initial HTTP password exchange confidential.

Target `/state` exports only resources belonging to that target, excluding execution projections. Owner routing strips incoming browser credentials and forwarding headers, checks destination authorization, and refuses recursive aggregation and worker endpoints. A request forwarded to a remote chat home includes a destination-specific sealed delegation over the original identity, accepted content, roster/revisions and file ownership. Every worker validates it and its own current scope. Management tools always execute locally to their Echo worker. No filesystem path implicitly refers to another host.

Chat homes persist a dispatch journal alongside user messages, runs and accepted request IDs in one transaction. Hosts reserve all required local bots before execution; the coordinator acquires hosts in stable order, releases partial reservations and retries busy hosts. Prepared reservations expire. Each worker transactionally accepts its identity before running, so lost start responses are safe to retry. A crash marks accepted running/prepared work interrupted and never automatically repeats tools. Models are snapshotted per node and validated at the destination; a remote-only turn does not require an entry-host model.

`bot_send`, `bot_reply` and `bot_wait` use the home coordinator's fixed roster and correlation IDs. Durable commit hooks run before queue visibility, explicit wakeup, reply or drain. Circular waits and unmentioned targets are rejected. Worker scopes do not contain owner credentials. Handoffs to unavailable hosts fail while independent workers continue. Workers may complete without their home and retain results for later reconciliation; chats never automatically change homes.

Worker snapshots carry a source epoch and sequence. Message/run merges and delivery checkpoints commit transactionally; stale snapshots cannot publish state. Worker message IDs are qualified by their source. Cancellation is journaled before transmission, retries after outages, and also covers worker projections on deletion. Persistent chat tombstones reject late acceptance and result merges. Stored schema version 2 adds tombstones and source checkpoints; version 3 retains superseded source epochs without rewriting existing chats or changing local IDs; newer unknown schema versions fail explicitly.

Schema version 4 adds the notification journal, browser devices, and durable per-device delivery claims/outbox. Final replies commit their alerts with the transcript; validated question sets create pending alerts, resolved when answered, canceled, interrupted, or deleted. Replica merges create alerts only at the visible chat home and do not replay already completed messages. Entry servers recover authorized peers' alert journals without browser sockets. Browser device management remains entry-local; subscriptions are bound to owner sessions, while VAPID keys use the credential store. Live clients and the background sender atomically compete for each device/alert, with a two-second live grace period. Committed push delivery uses encrypted Web Push and public HTTPS destinations, never silent push. Worker notification clicks carry chat, bot, and message targets through the existing hash router.

`InstanceClient` binds JSON, binary/media and event operations to one owner. Combined state deduplicates chats by home and ID. Opened remote transcripts and directory snapshots are cached at the entry host for offline reading; new messages still require a reachable home. Event recovery maintains independent source sequence/epoch state, applies snapshots and replays bounded backlogs without allowing an old recovery to overwrite a newer one. App windows, renderer choices, Monaco model/recovery keys, drafts, bookmarks and subscriptions all include ownership. Dirty editor buffers survive outages and saves revalidate disk revisions after reconnect. Existing local browser data is retained. Native file reveal requires a local owner connection on the file's host.

Remote HTML stays in the opaque-origin sandboxed iframe bridge. Native remote apps must match the host-owned module registry and negotiated capability; remote manifests cannot load privileged frontend modules. Settings, schedules, plugin bridges, hosting and Development controls use their selected host. Remote restart polling checks that host's health identity and refreshes its resources without reloading other instances.

## Notes

The built-in `notes` plugin is app-scoped, enabled by default and registers the native `notes/main` view. Its manifest has no tools or capabilities for model execution. The host module registry negotiates `native-notes/1` independently of Monaco. Notes alone receives an optional combined inventory accessor in `NativeAppContext`; existing apps keep their machine-bound context. Notes uses one `InstanceClient` per authorized owner, so unavailable peers never block local requests.

Owner-authenticated routes under `/api/v1/plugins/notes/notes` provide GET collection, POST creation, and GET/PUT/DELETE item operations. PUT accepts title, Markdown, resolved mentions and the expected revision; DELETE requires `?revision=N`. Each owner enforces plugin enablement. Private `notes` records use the existing SQLite namespace table with no schema migration. Transactional revision checks return 409 on stale writes and 404 on missing notes; updates never upsert. Note IDs, timestamps and revisions are server-owned. Mention ranges are half-open UTF-16 source offsets with stable node/bot IDs and historical labels; the server validates range/text consistency. Notes do not enter general state snapshots, model context or the plugin storage bridge.

The native view tokenizes Markdown prose using `marked`, derives hashtags, and preserves unchanged mention bindings through edits. DOMPurify plus explicit URL handling sanitizes rendered GFM. IndexedDB caches loaded notes and dirty drafts by entry identity and owning machine. The UI revalidates revisions before saving recovered drafts, preserves conflicts, disables offline editing, and prunes revoked owners. Independent bounded requests refresh visible Notes every five seconds and on focus/inventory changes. There is no replication protocol or automatic legacy migration.

## Confluence

The built-in bot-scoped `confluence` plugin declares `confluence.search` and `confluence.read`. The shared WASI guest delegates these operations to `internal/confluence` through the host broker; tokens never enter the guest. Owner settings store a normalized Cloud/Data Center connection and a vault reference. Credential save/clear and connection tests use authenticated `/api/v1/plugins/confluence/credential` and `/api/v1/plugins/confluence/test` POST routes. A connection mutex serializes configuration and token changes; active operations, including owner tests, are canceled after successful changes. Plugin Authoring cannot change the connection or credential reference.

Cloud CQL uses REST v1 search, while reads resolve content IDs to v2 types before requesting pages, blog posts, inline/footer comments or attachment metadata. Scoped tokens use the fixed Atlassian gateway; Data Center uses its configured context path with REST v1. Pagination reconstructs only approved search parameters after validating the returned destination. Redirects are denied, requests have a 30-second deadline and upstream JSON is bounded to 16 MiB. Storage markup is parsed locally into Markdown without resource loading. Unicode body chunks carry connection/argument bindings and a version check, keeping tool responses within the WASI output limit without silently dropping the rest of a page. No schema migration or separate app view is required.

The same broker also exposes `confluence.users.search` and `confluence.users.current`. Name lookup constructs an escaped `user.fullname` CQL string and reads user records independently of content results; Cloud uses the dedicated user-search endpoint and Data Center uses general search. Pagination stays confined to the operation's endpoint and its continuation binding cannot cross into content search. Current-user identity comes from `/rest/api/user/current` and refers to the token account. Results include only returned profile identifiers and visible names/email; hidden fields are not fabricated. Bots resolve a named author first, then use the returned account ID or username/key in content CQL.

## Unix runtime and secrets

Linux native commands use bubblewrap with isolated PID/mount/network namespaces, read-only runtime/toolchain mounts, writable declared roots and scratch directories, and a hidden private profile. A trusted relay in the isolated network namespace connects only to the host's filtered HTTP/SOCKS proxy. Child seccomp rules deny Unix sockets and namespace/inspection escape primitives; the relay is not dumpable. DNS answers are checked against Internet/private-network grants and the resolved address is pinned when dialing. Direct network access is denied. Commands must support the provided HTTP(S)/SOCKS proxy for network operations; protocols that ignore it fail closed.

macOS uses a deny-by-default Seatbelt policy with explicit runtime/workspace/scratch paths, private-profile denial, and access only to the filtered loopback proxy. Linux/macOS execute native `/bin/sh` commands or literal direct-executable argument arrays, use clean per-invocation environments, bound output, enforce deadlines and cancel process groups. Linux PID isolation also kills detached descendants when its sandbox exits. Platform-specific native acceptance is required, especially for macOS sandbox/toolchain behavior.

Windows secrets remain in Credential Manager. Unix secrets use a per-profile AES-GCM vault, hashed filenames, key-bound associated data, owner-only regular files, atomic replacement and directory synchronization. The vault rejects linked keys and overly broad file permissions. It has no interactive unlock requirement. Profile protection is the trust boundary; the encryption key and data must be backed up together. `build.sh` builds the WASI runtime, frontend, native executable and optional release archive. Startup scripts explicitly install a per-user service/task only when requested; no owner password is placed in a service definition.

## HTTP surface

File-reference suggestions use a lazy, in-memory filename index for explicit workspace roots, separate from the bounded file-content search tool. The picker ranks exact names and normalized paths before prefixes, substrings, multiword and fuzzy matches, then limits the displayed results to 200. Each root indexes at most 250,000 entries; `.git`, `.hg`, `.svn`, `node_modules`, `.cache` and `.echo` contents are omitted from recursive scans but remain reachable through explicit authorized paths. Typed paths also find newly created entries before indexing finishes. Unbound absolute-path completion only reads the typed directory rather than indexing a drive.

Indexes refresh on demand after five seconds and invalidate after Echo file/process mutations. Streaming index results expose `X-Echo-Reference-Indexing` and `X-Echo-Reference-Incomplete` response headers without changing the `/references` JSON array contract. The browser debounces edits, cancels stale requests, polls while indexing and shows incomplete or empty-search status. Every returned path is checked through the invoking bot's filesystem scope, and selecting or submitting references retains the existing recipient-specific validation.

All paths below are under `/api/v1`. Local bootstrap requires a loopback connection and a local Host; remote bootstrap requires the configured password. Mutating browser requests reject foreign or opaque Origins.

Coordinated updates advertise the additive `development-update/1` capability. The entry instance freezes its authorized membership and one target commit, prepares independent native builds, and activates peers in descending relay depth with itself last. Orchestration endpoints reject Swarm callers; leaf endpoints use the authenticated origin's owner grant. Missing capabilities require a one-time local upgrade. The original host-local development endpoints remain available for compatibility.

Version-1 JSON records in `development-rollouts` and `development-updates`, plus the current update pointer in settings, persist acceptance, cancellation fences, launch intent, per-host errors, and logs without changing SQL tables or local IDs. A crashed preparation is reported as interrupted, never automatically rerun. Retries use new participant IDs only for unsuccessful hosts and retain the target. Restart recovery requires a matching compiled revision; health and development snapshots expose this revision alongside the process identity.

Activation closes new chat admission under the scheduler mutex and defers calendar occurrences. Accepted dispatches and handoffs remain live; new remote worker reservations receive a retryable maintenance response and partial reservations are released. A 60-second renewable lease prevents abandoned drains; waiting has no forced interruption deadline. Ready builds also expire without coordinator renewals. Replacement verification has a two-minute timeout. Cancellation cannot undo an installed replacement or a checkout fast-forward. Failed/unavailable peers do not prevent other eligible hosts from progressing.

Development operations use the same owner sessions and Origin checks for local and remote users, and are not exposed through bot tools or plugin bridges. `internal/development` serializes operations and settings changes, runs builds independently of request lifetimes, and retains logs beneath the profile. Operation states are `running`, `succeeded`, `failed`, `restarting`, and `stopping`; concurrent actions return 409. Operation status is process-local; settings persist without a database schema migration. Update checks fetch only the configured upstream and compare immutable commits; applying an update revalidates the branch/upstream/HEAD and merges fast-forward-only with autostash disabled. The Windows launcher reports readiness before the host shuts down, waits for that process handle to exit, and replaces the staged executable. Both platform launchers set `ECHO_NO_OPEN=1` in the replacement process, including coordinated updates, so only an initial executable launch opens the installed PWA or browser. `-no-open` also suppresses the initial window for background startup. Restart polling uses process identity rather than requiring an observed outage.

Clients buffer incoming events during recovery, apply a snapshot, then replay events newer than its watermark. Slow subscribers disconnect and recover from persisted state and active buffers. The event log itself is not written per token.

The core composer stores plain text plus atomic bot/file reference segments. Optional segment `range: {start, end}` values are half-open UTF-16 offsets into `content`; file segments also carry a server-derived `kind` (`file` or `directory`). Each file occurrence retains its own path, including when labels repeat. The server validates file ranges, masks those spans when detecting bot recipients, and recomputes access on send. Existing messages without ranges remain readable; the UI only associates legacy file descriptors with unambiguous text occurrences. Native reveal remains host-local and loopback-only, with the same filesystem containment checks as changed-file reveal. No database migration is needed because segments are stored in the existing serialized message.

## Plugin ABI and package sources

Named bots store plugin selections at creation. An absent selection denies bot-scoped plugins; Echo alone treats an absent selection as enabled. Global enablement, pending approval and plugin scope still gate availability. The version 5 storage migration snapshots legacy implicit selections from the saved catalog before built-in registration, so upgraded bots retain prior access without receiving plugins introduced by the new build. App-scoped plugins continue to use global availability.

A plugin may explicitly register one primary GUI with `app: {"viewId":"main","icon":"data:image/svg+xml,..."}`. `viewId` must name a floating or embedded view; `icon` is optional and accepts SVG, PNG, JPEG or WebP data URLs capped at 256 KiB. The catalog uses the plugin's ID and name, and displays icons as images with initials as a fallback. Registration is included in the immutable package digest and rollback. It adds no privileges; the existing `scope: "app"` denotes app-wide permission scope and does not register a GUI. App views without registration are not listed in Apps. The UI template and HTML-only `plugin_install` shorthand emit registration; complete manifests must opt in.

Apps and dock launches use Echo's bot context and fetch the current app view with that context, without broadcasting a launch to other browsers. The browser maintains one window per plugin/view/bot, coalesces concurrent opens, and focuses existing windows without reinitializing their contents. State refresh closes windows when effective availability changes, their view disappears, or their package digest changes. Chat-driven `plugin_open` defaults to the registered view, then the first floating or embedded view; renderer views cannot be launched. Plugin startup continues to use the iframe ready/init handshake below.

`View.kind` chooses the initial presentation: `embedded` or `floating` (the default for existing manifests). The shared app-view host keeps each iframe in one attached DOM container, changing only geometry and visibility. Its controls switch modes or close the view; local storage retains presentation and floating geometry. `#app/{pluginId}/{viewId}/{botId}` fills the main content area, leaving sidebar/dock access. Sidebar chat and Apps navigation hide embedded instances. The compact embedded title bar has a pop-out icon and Close control. Chat DOM, drafts, attachments, selected bot thread and streaming remain mounted. Bot-scoped plugins have isolated live instances; app-scoped plugins have one instance per browser.

Monaco Editor is an app-scoped built-in (`monaco-editor/main`), initially embedded. `web/src/builtinApps.ts` is the host-owned lazy native-module registry; installed manifests cannot claim built-in provenance or native execution. Ordinary HTML views retain their opaque-origin iframe sandbox and restricted nonce bridge. Monaco 0.56.0, virtual-core 3.17.7, codicons 0.0.46-24 and language workers are bundled locally. Monaco's vendored DOMPurify is replaced at build time by an isolated instance of Echo's patched 3.4.17 dependency. The Terminal also ports its xterm and native PTY dependencies without runtime imports from OLD.

The bot dropdown selects independent editor sessions. Monaco model URIs include node, bot and root IDs, preventing shared folders from sharing buffers or undo history between bots. Switching bots retains live models, navigation, tabs, tree state and selections. IndexedDB `echo2-monaco-editor` / `bot-sessions` stores recovery drafts, tab state, tree expansion and positions. Old workspace sessions/settings are not imported. Initial bot selection uses the last valid selection, then launching bot, then Echo; bots with no folders support untitled editing and expose Configure Folders. Explicit closure prompts Save/Discard/Cancel across sessions; hiding the app does not close them. Disabling the plugin or deleting a bot disposes its live readers/watchers while retaining browser recovery data.

`internal/editorfs` serves owner-authenticated filesystem operations under `/api/v1/plugins/monaco-editor/bots/{botId}/fs`. Every access resolves current configured bot roots; empty roots grant no access. Root IDs hash canonical paths. File references remain `{rootId,path}`; rooted I/O rejects traversal and symlink escapes, and private profile state is excluded from listing, indexing and mutations. Text reads/saves are capped at 10 MiB and media at 500 MiB. Saves compare disk revisions and replace files atomically; create-only writes cannot overwrite occupied paths. Trash copies and verifies through pinned roots before removal, retains recoverable payloads after cleanup failures, and refuses restore collisions. Search supports filters, unsaved-buffer overlays, and revision-checked replacements. No legacy workspace manager is used. File mutations pass through the shared source-control coordinator before writing, while retaining the rooted filesystem boundary.

The per-bot `events` WebSocket reference-counts recursive filesystem watches and accepts expanded/open file references. Sequence gaps and overflow trigger a resync; clients fall back to polling when disconnected. Reads after changes reload clean buffers and flag dirty conflicts. Current root changes refresh subscriptions; disposal/disconnection releases them. Bookmarks live in the existing records store under `editor-bookmarks/{botId}`, including position updates and path remapping. Editor preferences use the plugin config. The editor ports tabs, explorer, search, outline, bookmarks, Markdown/media previews, conversions and legacy hotkeys; bundled language services remain available. Side chat, external language servers, SCM UI, debugging and test/coverage runners are absent. The separate Terminal plugin remains accessible below the editor. Inline chat is available through Ctrl+I/Cmd+I.

Terminal is an app-scoped built-in (`terminal/main`), enabled by default. The host's `isBuiltinDock` allowlist routes Apps, sidebar and `plugin_open` launches to a persistent dock under the main content instead of creating a floating/embedded instance. Ordinary plugins cannot claim this presentation or its native privileges. Bot choices include machine-qualified identities; selectors, controller state and preferences remain separate from chat routing. Generic workbench panel hooks remain available to future trusted integrations; debugger/test/Docker services are not ported.

`internal/terminal` owns one interactive PTY per bot using go-pty 0.2.3 (ConPTY on Windows, Unix PTYs elsewhere). Windows prefers pwsh then Windows PowerShell; Unix uses the absolute `$SHELL` or `/bin/sh`. These explicitly owner-operated shells use host permissions, independently of the restricted AI process broker. `/api/v1/plugins/terminal/bots/{botId}` provides authenticated `sessions` create/list, individual snapshots with `afterSequence`, input, size, stop/restart and folder shortcuts, plus saved-command CRUD and an `events` WebSocket. Guards check current plugin availability and bot identity; session IDs cannot cross bot boundaries. Folder requests resolve current bot roots and quote paths for the shell. Process trees are cleaned up on stop, plugin disablement, bot deletion and shutdown, including sessions with no browser attached.

Terminal events carry bot/session identity and monotonic output sequences, with base64 byte payloads. A 2 MiB per-session replay buffer supports reload/reconnect; gaps and overflow markers trigger snapshots. Input is UTF-8 chunked below the 64 KiB server cap, serialized, and never retried. Disconnects invalidate queued input, including pending clipboard reads. Resize is serialized/coalesced and repeated after reconnect. Xterm 6.0.0, fit 0.11.0 and web-links 0.12.0 preserve the original dock behavior. Remote requests/events use `InstanceClient` and existing authenticated Swarm transport gated by `native-terminal/1`, without host fallback.

Saved commands use records namespace `terminal-commands` keyed by bot ID on the owning server, with serialized mutations and stable order. No schema migration or legacy import is needed. Browser storage keeps bot selection per entry node and dock height/open/maximized state per entry node and machine-qualified bot. PTYs and replay are memory-only; ordinary browser detach leaves the shell alive, but server restart does not recover a process.

Dock ordering is stored under `settings/app-dock` in the existing records table. Owner mutations are serialized, idempotent per plugin, and publish `changed` after successful persistence; no schema migration is required. Only currently available registered apps are shown in the dock, while saved IDs survive disablement, pending approval and registration removal. Unpinning remains possible for unavailable entries. `#apps` selects the catalog while conversation DOM, drafts and event processing remain mounted.

ComfyUI is a built-in bot-scoped plugin with `comfyui.generate`, `comfyui.generate_video`, `comfyui.save_image`, and `comfyui.save_video` capabilities. Its WASI guest delegates to the host's endpoint-confined ComfyUI client. The owner selects the HTTP(S) server; models cannot expand that grant, and requests reject redirects. Workflow and input-image reads and binary output saves go through the rooted file broker. Generated bytes bypass WASI/model JSON and are compressed into attachment storage, linked immediately to the tool message. Metadata is hydrated from those rows on recovery, and deletion follows the chat's existing foreign-key cascade. The browser renders tool attachments outside collapsed work. Generated image content is inserted after a complete tool-result group for the originating bot; video results stay metadata-only. This port preserves workflow precedence, image upload precedence, all image/video template controls, first-output display, and workspace save tools from `OLD/`.

Jira is a built-in bot-scoped plugin that starts disabled. The existing WASI guest delegates `jira.search`, `jira.issue`, and `jira.comments` to the host's `internal/jira` client. A shared per-machine connection uses Cloud v3 enhanced JQL search/token pagination or Data Center v2 search/offset pagination. Scoped Cloud tokens use a fixed gateway base derived from the owner-supplied Cloud ID. Credential references live in plugin records; actual tokens stay in the host vault. Owner-only credential/test routes and the dedicated settings form use the selected machine's API. Connection identity changes clear and delete the old credential; enablement changes retain it. Jira configuration mutations are serialized and cancel active plugin invocations through `Plugins.Save`.

The Jira client exposes fixed read operations, rejects redirects, validates issue IDs and configured base paths, preserves normal TLS verification, and applies 30-second request deadlines and an 8 MiB upstream response cap. Raw tokens and Basic authorization values are redacted before results/errors enter WASI. Results are capped at 1 MiB; full-issue reads collect comment pages with explicit continuation and incomplete/error metadata when needed. Field-name/schema mappings and structured custom fields remain intact; ADF fields/comments gain readable text. No Jira writes, binary downloads, changelog traversal, database migration or standalone app registration are introduced.

Manifests declare API version `1`, ID/version/scope, capabilities, tools with argument schemas, model-provider/renderer identifiers, views and settings. Compatible HTTP model connections and Markdown View are the built-in provider/renderer implementations. Backend source templates and UI bridge examples live in `internal/plugins/templates` and are also available through `plugin_template` in chat.

Custom providers name their backend entry tool in `providers`. Select that provider in the connection editor. Echo validates availability for every recipient and supplies `{messages,tools,generation}`; providers return `{content,reasoning,toolCalls,finishReason}`. `model.complete` delegates to the compatible streaming client. Other protocols use `model.request` (bounded GET/POST with an endpoint-relative path and host-injected credential) and `model.emit` (content/reasoning deltas). These capabilities exist only inside the selected provider invocation, are pinned to that connection, and require owner approval. Provider entries are excluded from the model's ordinary tools. Model discovery remains the optional compatible `/models` request; manual identifiers work for other protocols.

Custom renderers name a `kind: "renderer"` view in `renderers`. An isolated frame sends `renderer-ready`, receives `init` with nonce/theme, and answers `render` with `{type:"rendered",nonce,id,html}`. Echo accepts only outstanding requests owned by that frame, only for assistant messages, and sanitizes output. Enabled custom renderers take precedence over Markdown, ordered by plugin ID. Bot toggles apply before sending text. With every renderer disabled, core output stays plain text. The `provider` and `renderer` authoring templates demonstrate both contracts.

A backend receives one JSON object on stdin: `{tool, method, params}`. It writes exactly one `{result: ...}` or `{error: "..."}` object to stdout. The `echo.call(ptr, length, out, capacity)` WASM import brokers privileged operations. A zero-capacity call executes the request and returns the output size; the second call copies that response. Tools may implement pure computation without capabilities.

Broker methods include `file.read/write/list/search/delete/move/mkdir`, `web.get`, `process.run`, and `storage.get/set/delete`; the built-in packages additionally use their management/calendar operations. Files/processes use the invoking bot's effective scope. Storage is keyed by plugin ID and bot ID, with 1 MiB values and an 8 MiB namespace quota. A plugin cannot select another namespace. Model credentials are held in the host credential vault and never enter WASI or iframe environments.

UI views run with `sandbox="allow-scripts"`. App-frame CSP permits remote scripts, styles, images, fonts and media only from approved HTTP(S) origins, while denying direct connections, framing, forms and workers. Renderer frames retain their existing isolated contract. A view sends `echo-plugin-ready`; Echo returns `echo-plugin-init` with a nonce, identity and theme. Requests include `{type:"echo-plugin-request", nonce, pluginId, viewId, id, method, params}`. The parent bridges `window.close`, declared namespaced storage and approved network methods. Responses echo `id` and the nonce. Echo alone owns geometry and persists window placement.

### Inline editor chat

`POST /api/v1/plugins/monaco-editor/bots/{botId}/inline-chat` is an authenticated, editor-guarded NDJSON stream. Requests carry the current buffer, UTF-16 selections, file references, inline history, optional prior proposal, and the existing generation settings. The server resolves the bot and endpoint on the owning machine and uses the shared provider/credential pipeline. Ephemeral dispatches use the normal per-bot admission and revocation barriers without creating durable chat/run records. Request disconnect, Stop, scope revocation, plugin disablement and server shutdown cancel execution and release reservations.

The inline runner exposes only file/skill reads and `propose_inline_edits`. It validates edits atomically and emits complete candidate buffers and end-exclusive line changes; it never writes files. Current-file reads use the supplied candidate rather than disk. Context and proposals are limited to 256 KiB, history to 128 messages, references and selections to 32 each, and tool exchanges to 24 rounds. Oversized context and interrupted streams produce explicit errors without silently truncating buffers. The browser rechecks model content and disk revision before accepting an undoable buffer edit; normal editor saving retains its revision checks.

The legacy inline widget, mentions and preview CSS are isolated to the code plugin. A shared `GenerationSettings` component renders chat and editor controls in a positioned top-layer popup. Editor preferences are stored under `echo2:inline-generation:<nodeId>:<botId>`; conversations remain in memory under machine-qualified bot/tab keys. Settings callbacks supplied through `NativeAppContext` seed defaults and open the correct machine's model settings without changing the main chat's choices.


### Custom plugin network grants

API 1 manifests may declare `network: {"origins":["https://api.example.com","wss://stream.example.com","http://localhost:8080"]}`. Exact origins are normalized, deduplicated and included in package digests and rollback. Paths, wildcards, credentials, queries and fragments are rejected. Grants cover every path, including private addresses to which that origin resolves. New origins require direct owner approval using the existing digest-bound approval; reductions retain approval. Settings list all destinations and highlight newly requested and recognizable private addresses. Custom plugins without declarations receive an actionable denial, including legacy `web.get`; built-in tools and connection-bound model operations keep their existing policies.

Declare each method in `capabilities`: `web.request` (or compatible `web.get`), `websocket.open`, `websocket.send`, `websocket.receive`, `websocket.close`. HTTP requests accept `{url,method,headers,body,encoding}`; encoding is `text` (default) or `base64`. Responses contain `{url,status,headers,contentType,content,encoding}`; header values are arrays. Supported methods are GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS. The broker checks every redirect, drops all caller headers on cross-origin redirects, and never forwards ambient cookies or Echo credentials. Request/response bodies are limited to 1 MiB; serialized results remain below the existing 2 MiB ABI limit. Requests time out after 30 seconds. Explicit authorization/API-key headers are supported, but cookies and transport-controlled headers are reserved.

WebSocket `open` accepts `{url,headers,protocols}` and returns `{handle,protocol}`. `send` accepts `{handle,data,encoding,binary}`; `receive` returns `{data,encoding,binary}`; `close` accepts `{handle}`. Binary data uses base64. Handles are isolated to a WASI invocation or app relay. Each session permits 16 sockets, one pending receive/send per socket, 1 MiB messages, and at most 4 MiB/256 messages queued for a slow consumer. Oversized messages or slow consumers fail and close the connection. Handshake redirects are rejected. Backend handles close at invocation end.

`GET /api/v1/plugins/{id}/network?botId=...&viewId=...&digest=...` is an owner-authenticated WebSocket relay opened only by the trusted parent through its instance-bound client. Requests are `{id,method,params}` and responses are `{id,result}` or `{id,error}`. At most 32 calls/4 MiB may be outstanding. The parent maintains the iframe nonce/source/identity checks and forwards network calls over this relay. Package saves revoke its lease; window closure, disconnect, owner-session revocation, bot/plugin disablement and host shutdown cancel active traffic. HTTP bridge callers include the reviewed digest. The UI template includes promise-based `echoCall` and an event-based `echoSocket` example.

API and WebSocket traffic originates on the plugin's Echo machine, including when routed through Swarm. Static assets load from the viewing device and remain subject to CSP, mixed-content, CORS and browser private-network policies. An HTTP origin's CSP source follows browser scheme-upgrade rules. Remote assets do not receive Echo host credentials. No raw TCP/UDP or new credential vault interface is exposed.


## Monaco source control

`internal/sourcecontrol` multiplexes Git, Fossil, and P4 adapters. `internal/gitservice` supplies Git parsing and transactions; `internal/scmexec` is the narrow execution/configuration boundary. Adapters own discovery, native sections, metadata, baselines, actions, and hunk capabilities. The frontend presentation registry supports provider-specific row actions, commit behavior, and repository menus without introducing Git staging semantics into a new provider. History and Fossil protected snapshots are not exposed in this pass.

The owner-authenticated `/api/v1/plugins/monaco-editor/bots/{botId}/source-control` API uses opaque repository IDs and scoped file references. The existing instance router sends requests and events to the bot's owner. Opening Source Control starts bounded recursive discovery and subscribes to status events. Scans skip linked directories, VCS internals, dependency/cache directories, ignored directories, and denied profile paths. Overlapping workspace roots retain their scope mappings. Partial scans report diagnostics alongside any repositories already found. Parent search is opt-in and never grants metadata access or authority to mutate an enclosing checkout.

Commands use the enabled Git/Fossil/P4 plugins' configured executables, network grants, and protected credentials through the native process broker. Structured capture separates bounded stdout from stderr and preserves file bytes; existing CLI callers retain combined streamed output. Repository/client locks serialize mutations. Revision and hunk tokens reject stale operations; failures refresh actual status without automatically replaying writes. Git working revert restores the index version without unstaging, and discarded untracked files use Echo Trash.

Fossil supports a repository database beside its checkout. The host reads the checkout's SQLite `vvar.repository` reference in read-only mode before each command. When that file is in the checkout's immediate parent, Fossil commands receive a provider-specific grant to that folder so SQLite can manage its journal files. This deliberate metadata exception does not change bot roots, editor/file-tool access, or discovery scope. Other external locations require an explicitly configured workspace folder; linked databases and folders containing Echo private state are rejected. Fossil UI uses the same repository validation.

Ordinary Fossil working diffs fetch their baseline with `finfo` and read the current file through the editor filesystem. Buffer-only hunk revert does not run checkout-wide conflict/hash scans or fetch manifest permissions. It retains the local symlink guard, undoable buffer editing, and filesystem revision checks on save. Legacy protected-snapshot paths retain their separate validation.

Git diff requests reuse their index metadata read for both submodule detection and hunk validation. Working diffs fetch the filtered index baseline directly after a size check, avoiding an additional raw-content read. This reuse is confined to one request: hunk mutations still recompute tokens, including current index/HEAD/attributes, before changing the index. Binary and oversized content retain explicit fallback states.

Windows SCM commands reuse filesystem grants only for an identical bot/provider, executable, roots, toolchains, and network capability set. Each invocation retains its own scratch directory and terminating job, and commands within a sandbox session run serially. Bot scope changes and shutdown cancel active sessions and revoke their grants; durable ACL journals handle crash recovery. Recovery and session shutdown batch revoked identities by case-insensitive path, requiring one inherited ACL traversal per location. Unrelated grants are preserved, failed records remain durable for retry, and startup logs recovery progress before accepting HTTP requests. Ordinary shell/tool calls remain per-invocation. This avoids recursively rewriting a large checkout's ACLs for every status command. Provider availability checks resolve configuration/executables without launching version commands against the workspace. The sidebar renders before discovery, deduplicates concurrent requests, cancels on disposal, and presents a retryable timeout instead of remaining blank.

Monaco diff tabs share working-copy models with ordinary file tabs and participate in tab disposal and session recovery. Staged and stash models are immutable. Split mode is explicit even in narrow windows. A shared horizontal scrollbar uses the larger content range and pads the shorter pane's scroll range so both can move equally. Arrow hunk actions edit the buffer with Undo/Redo; staging requires saved content and validates server-side content/index tokens. Binary, oversized, unsupported text, submodules, and missing revisions have fallback states.

P4 settings and registration journals live under the current profile's `source-control/p4` directory. First successful discovery enables tracking; a saved disable choice is retained. Folder overrides inherit the current P4 plugin defaults. Passwords/tickets are protected by the existing credential vault and keyed to server/user identity. Editor saves, replacements, Explorer operations, structured file tools, and generated-image writes share a mutation coordinator: required checkout precedes disk writes, and failed post-write registration returns a pending diagnostic and durable recovery record. Trash records retain the original recovery identity. External changes remain candidates until a reviewed, token-validated reconcile preview is applied; an empty selection never means the whole workspace. Tracking watches survive sidebar closure; subscribed metadata polls every five seconds and backs off to thirty seconds after failures.

Fossil UI is exposed as an authenticated, read-only native HTTP view through Echo's scoped runner, without starting an unconfined host listener. Repository history, Fossil protected snapshots, and P4 submit/shelving/stream administration remain outside this UI. There is no import of OLD profile settings or recovery data.
